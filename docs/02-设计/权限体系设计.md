# 权限体系设计文档

## 概述

系统采用 **RBAC（基于角色的访问控制）** 模型。权限挂载到角色，用户绑定角色。支持动态创建角色和分配权限。

## 角色

| 角色 | 类型 | 说明 |
|---|---|---|
| `admin` | 内置默认 | 管理员，拥有全部平台权限 |
| `moderator` | 内置默认 | 版主，帖子/评论/版面/标签/举报管理等，不含角色管理和系统设置 |
| `user` | 内置默认 | 普通论坛用户，仅基本读写：发帖、评论、看用户、看角色、举报 |
| `ban` | 内置默认 | 封号用户，无任何权限 |

角色通过 `roles` 表存储，通过 `role_permissions` 关联表多对多绑定权限。

### 账号封禁 vs 禁言

- **账号封禁（role = "ban"）**：账号级别封禁。用户登录时直接拒绝颁发 token。封号时应同步吊销全部 token
- **禁言（Banned 表）**：操作级别禁止发言。用户仍可登录，但网关 `banCheck` 拦截写操作

两者是两套独立机制，不可混淆。

## 数据模型

### Permission（权限定义）

```go
type Permission struct {
    ID          uint      // 主键
    Code        string    // 权限码，唯一索引，如 "post:create"
    Name        string    // 中文名，如 "创建帖子"
    Description string    // 描述
    CreatedAt   time.Time
}
```

表名: `permissions`

### Role（角色）

```go
type Role struct {
    ID        string    // 主键
    Name      string    // 角色名，唯一，如 "admin"
    CreatedAt time.Time
}
```

表名: `roles`

### RolePermission（角色-权限关联）

```go
type RolePermission struct {
    ID           uint   // 主键
    RoleName     string // 角色名（索引）
    PermissionID uint   // 权限 ID（索引）
}
```

表名: `role_permissions`

## 权限检查

- **后端**: `PermissionService.HasPermission(roleName, permCode) bool` — 查询进程级缓存
- **中间件**: 网关 `banCheck`（Enforce 阶段）拦截被封禁用户的写操作
- **前端**: `api-client` 的 `PermissionCode` 常量提供权限码枚举

## 初始化流程

1. 应用启动 → `seeds` 写入 4 个默认角色
2. 写入 32 个默认权限到 `permissions` 表
3. 根据 `DefaultRolePermissions` 映射建立角色-权限关联
4. 加载角色缓存到进程内存 (`LoadRoleCache`)
5. 完成后设置 `meta.seeded = true`，下次启动跳过 seed

## 版块级（Space-Scoped）权限

在全局 RBAC 之上叠加**覆盖式**版块级权限：

- 表 `space_role_permissions`（space_id, role_name, permission_id）存储「某版块为某角色配置的权限集合」。
- 解析 `HasPermissionInSpace(role, spaceID, code)`：若 (spaceID, role) 存在覆盖（≥1 条记录），该版块内**完全用这套替换**全局；否则回退全局。
- 约定：覆盖必须 ≥1 个权限；「无记录」即「回退全局」。在某版块把角色权限收回到 0 不在范围内。

**作用范围**（资源归属版块的写操作）：

| 操作 | 权限码 | space_id 来源 | 检查位置 |
|---|---|---|---|
| 编辑/删帖 | `post:update` / `post:delete` | post.SpaceID | service |
| 置顶/锁定 | `post:pin` / `post:lock` | post.SpaceID | service |
| 删评论 | `comment:delete` | 评论所属 post.SpaceID | service |
| 编辑/开关版块 | `space:update` | URL space_id | middleware |
| 版块禁言/解禁 | `user:update` | URL space_id | middleware |

全局不变：role:manage、setting:manage、stats:read、user:read/delete、space:create/delete、前台读操作。

**接口**：`POST /permission/space`（读）、`/permission/space/sync`（设置覆盖）、`/permission/space/clear`（清除覆盖，回退全局）。

## 已知差异

- `comment:update` 权限码在后端和前端均已定义（本任务中完成前端添加）。
- `reconcile:counters` 权限仅在后端定义，无对应前端 UI 入口。此为刻意设计——修复计数器的操作由后端自动触发或管理员手动通过 API 调用，无需前端界面。

除此之外，前后端权限码完全同步。

## 已知取舍

以下源于首次实现（2026-06-13）的显式设计决定，非缺陷，后续可按需重评：

1. **Space Delete 保持全局**：删除版块仍走 `RequirePermission(PermSpaceDelete)` 全局检查，不走 `RequireSpacePermission`。因删除版块是破坏性操作，不希望版块级覆盖影响此门控。
2. **Content.Create 无 service 层权限检查**：路由中间件 `RequirePermission(PermCommentCreate)` 提供唯一授权层。service 层的 `Create` 不重复检查——与 post/pin/lock 的"service 层权威"模式不一致，但刻意保留以避免在评论创建热路径上增加版块级查询。
3. **版块覆盖必须 ≥1 权限**：空权限数组被 handler 层 `INVALID_PARAMS` 拒绝。清除覆盖必须显式调用 `/clear` 接口。此设计避免"空集合 = 无覆盖"的歧义。
