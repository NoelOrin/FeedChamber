# 百万级社区文章本地搜索引擎技术方案

## 一、背景与需求

社区文章场景对搜索引擎的要求：

- **数据规模**：百万级文章，单篇平均 2000-5000 字
- **查询模式**：关键词搜索为主，需要相关性排序
- **更新频率**：文章实时发布/编辑，索引需增量更新
- **部署约束**：轻量级，无外部依赖，单机运行
- **语言**：中文为主，需支持中文分词

---

## 二、技术选型

### 候选方案对比

| 方案 | 查询延迟 | 索引大小 | 内存占用 | 中文支持 | 增量更新 | 运维复杂度 |
|------|---------|---------|---------|---------|---------|-----------|
| **Tantivy** | 1-5ms | 原文1.1x | 150-200MB | 优秀 | 支持 | 低 |
| SQLite FTS5 | 30-80ms | 原文1.3x | 低 | 一般 | 有限 | 极低 |
| Meilisearch | 5-15ms | 原文2-3x | 2-4GB | 优秀 | 支持 | 中 |
| Elasticsearch | 10-30ms | 原文1.5x | 2GB+ | 优秀 | 支持 | 高 |
| Xapian | 2-10ms | 原文1.2x | 200-300MB | 一般 | 支持 | 中 |

### 选型结论：Tantivy

**推荐理由：**

1. **性能与资源的最优平衡**
   - 百万文档查询延迟稳定在 1-5ms，优于 SQLite FTS5 一个数量级
   - 内存占用控制在 200MB 以内，远低于 Meilisearch/Elasticsearch
   - 索引膨胀率仅 1.1 倍，存储效率最高

2. **架构轻量**
   - 嵌入式搜索引擎，无需独立服务进程
   - 单二进制/库依赖，无外部组件
   - 索引即文件，备份/迁移简单

3. **增量更新能力**
   - 支持文档增删改，无需全量重建
   - 段合并（segment merge）自动优化索引
   - 适合文章实时发布的场景

4. **Rust 生态优势**
   - 内存安全，无 GC 暂停
   - 并发性能好，适合高并发查询
   - 可通过 FFI 集成到 Go/Python/Node 等语言

5. **中文分词成熟**
   - `tantivy-jieba` 提供原生 Rust 分词
   - 支持自定义词典，适应社区领域术语
   - 分词性能优于 Python 版 jieba

### 索引 Schema 设计

```rust
let mut schema_builder = SchemaBuilder::new();

// 文章ID，用于去重和更新
schema_builder.add_text_field("article_id", STRING | STORED);

// 标题，高权重
schema_builder.add_text_field("title", TEXT | STORED);

// 正文，标准权重
schema_builder.add_text_field("content", TEXT);

// 标签，精确匹配 + 搜索
schema_builder.add_text_field("tags", STRING | STORED);

// 作者
schema_builder.add_text_field("author", STRING | STORED);

// 发布时间戳，用于时间排序
schema_builder.add_i64_field("published_at", INDEXED | STORED);

// 热度分，用于排序加权
schema_builder.add_f64_field("hot_score", INDEXED | STORED);

let schema = schema_builder.build();
```

### 字段权重设计

| 字段 | 权重 | 说明 |
|------|------|------|
| title | 2.0 | 标题匹配权重最高 |
| content | 1.0 | 正文标准权重 |
| tags | 1.5 | 标签匹配高于正文 |

查询时通过 `boost` 参数调整：

```rust
let title_query = TermQuery::new(...).boost(2.0);
let content_query = TermQuery::new(...).boost(1.0);
```

## 四、中文分词方案

### 分词器选择：tantivy-jieba

**优势：**
- Rust 原生实现，无 FFI 开销
- 分词速度：~50MB/s（单核）
- 支持自定义词典
- 与 Tantivy Tokenizer 接口无缝集成

### 自定义词典策略

社区文章包含大量领域术语，需维护专业词典：

```
// custom_dict.txt
前端开发
后端架构
微服务
容器化
...
```

**词典维护流程：**

1. 初始词典：jieba 内置词典 + 社区高频词提取
2. 动态扩展：新文章发布时，提取未登录词加入词典
3. 定期优化：分析搜索日志，补充热门查询词

### 同义词处理

```rust
// synonyms.txt
容器化=容器=Docker
微服务=微服务架构
AI=人工智能=机器学习
```

通过 `SynonymFilter` 实现同义词扩展查询。

## 五、排序算法

### 多因子排序模型

最终得分 = BM25 相关性 × 时间衰减 × 热度权重

#### 1. BM25 相关性（Tantivy 内置）

```rust
// Tantivy 默认 BM25 公式
score(D, Q) = Σ IDF(qi) · (f(qi, D) · (k1 + 1)) / (f(qi, D) + k1 · (1 - b + b · |D|/avgdl))
```

参数调优建议：
- `k1 = 1.2`（词频饱和参数，社区文章适用）
- `b = 0.75`（文档长度归一化参数）

#### 2. 时间衰减

新文章权重更高，公式：

```rust
fn time_decay(published_at: i64, now: i64) -> f64 {
    let hours = (now - published_at) as f64 / 3600.0;
    1.0 / (1.0 + hours / 24.0).ln()  // 对数衰减，24小时半衰期
}
```

#### 3. 热度权重

综合点赞、评论、分享等互动数据：

```rust
fn hot_score(likes: u32, comments: u32, shares: u32) -> f64 {
    let raw = likes as f64 * 1.0 + comments as f64 * 2.0 + shares as f64 * 3.0;
    raw.ln()  // 取对数避免极端值主导
}
```

#### 4. 最终排序

```rust
final_score = bm25_score * time_decay * hot_score.powf(0.3)
```

热度权重指数 0.3 表示热度作为软排序因子，不完全压倒相关性。

## 六、性能优化

### 6.1 索引写入优化

**批量写入：**

```rust
let mut index_writer = index.writer(50_000_000)?;  // 50MB 内存缓冲

// 批量添加文档
for article in articles {
    index_writer.add_document(doc!(...))?;
}

// 批量提交
index_writer.commit()?;
```

**写入性能基准（百万文档）：**

| 批量大小 | 耗时 | 吞吐量 |
|---------|------|--------|
| 单条提交 | 45min | ~370 docs/s |
| 1000条批 | 8min | ~2000 docs/s |
| 10000条批 | 5min | ~3300 docs/s |

**建议**：异步队列攒批，每 1000 条或 5 秒提交一次。

### 6.2 段合并策略

```rust
let merge_policy = MergePolicy::default()
    .with_min_merge_size(8)           // 最小合并段数
    .with_max_merge_size(16)          // 最大合并段数
    .with_layer_size_multiplier(5);   // 层级倍数

index_writer.set_merge_policy(merge_policy);
```

**段合并时机：**
- 后台异步执行，不阻塞查询
- 建议在低峰期（凌晨）触发大规模合并
- 小规模合并随写入自动进行

### 6.3 查询性能优化

**查询缓存：**
```rust
// 热点查询结果缓存，TTL 5分钟
let cache = LruCache::new(1000);
```

**字段裁剪：**
- 搜索时只返回必要字段（article_id, title, snippet）
- content 字段不 STORED，节省内存和IO

**分页优化：**
```rust
// 避免深度分页，使用游标分页
let after_doc = searcher.doc::<Document>(last_doc_address)?;
// 基于 published_at 游标，而非 offset
```

### 6.4 内存控制

| 组件 | 内存占用 | 优化手段 |
|------|---------|---------|
| 索引段缓存 | ~80MB | 限制并发加载段数 |
| 查询缓存 | ~50MB | LRU 淘汰策略 |
| 写入缓冲 | ~50MB | 控制 writer 内存上限 |
| 分词词典 | ~20MB | 固定，不可压缩 |
| **总计** | **~200MB** | - |

### 6.5 并发模型

```
┌──────────────────────────────────────┐
│           应用进程                    │
│                                      │
│  ┌──────────┐    ┌──────────┐       │
│  │ 查询线程1 │    │ 查询线程2 │  ...  │
│  └────┬─────┘    └────┬─────┘       │
│       │               │              │
│       ▼               ▼              │
│  ┌─────────────────────────────┐    │
│  │    Searcher（共享只读）       │    │
│  └─────────────────────────────┘    │
│                                      │
│  ┌─────────────────────────────┐    │
│  │   Writer（单线程写入）        │    │
│  └─────────────────────────────┘    │
└──────────────────────────────────────┘
```

- Searcher 可多线程共享（只读）
- Writer 单线程，避免写冲突
- 更新索引后原子切换 Searcher

## 七、部署与运维

### 7.1 索引文件结构

```
/search-index/
├── meta.json          # 索引元数据
├── .managed.json      # 段管理信息
├── segment_*.json     # 各段数据文件
└── write.lock         # 写锁文件
```

### 7.2 备份策略

```bash
# 方案1：文件系统快照（推荐）
cp -r /search-index /backup/search-index-$(date +%Y%m%d)

# 方案2：冷备份（需停止写入）
rsync -av /search-index /backup/
```

### 7.3 索引重建

当 Schema 变更或索引损坏时：

```bash
# 从数据库全量重建
./rebuild-index --source db --batch-size 10000

# 预计耗时（百万文档）：5-8 分钟
```

### 7.4 监控指标

| 指标 | 正常范围 | 告警阈值 |
|------|---------|---------|
| 查询延迟 P99 | <10ms | >50ms |
| 索引大小 | <1.5GB | >2GB |
| 段数量 | <50 | >100 |
| 写入队列积压 | <1000 | >10000 |
| 内存占用 | <250MB | >400MB |

## 八、风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| 索引损坏 | 搜索不可用 | 定期备份 + 全量重建能力 |
| 分词效果差 | 搜索不准 | 持续优化词典 + 用户反馈 |
| 索引膨胀 | 磁盘占用高 | 定期段合并 + 清理过期文章 |
| 高并发写入 | 查询变慢 | 写入限流 + 异步队列削峰 |
| Schema 变更 | 需全量重建 | 兼容性设计 + 灰度迁移 |
