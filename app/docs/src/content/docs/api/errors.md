所有错误码定义在 `internal/pkg/errors.go`，网关与业务层共用。**不要自造号段。**

## 认证与凭证（1xxx → HTTP 401）

| 码 | 名称 | 默认文案 | 客户端该怎么做 |
|----|------|----------|----------------|
| 1001 | `TOKEN_NOT_EXIST` | 令牌不存在 | 跳登录 |
| 1002 | `TOKEN_WRONG` | 令牌错误 | 清本地凭证，跳登录 |
| 1003 | `TOKEN_EXPIRED` | 令牌已过期 | 跳登录（无 refresh 时） |
| 1010 | `INVALID_PASSWORD` | 密码错误 | 提示重试，注意限流 |
| 1011 | `USER_NOT_FOUND` | 用户不存在 | 提示 |
| 1012 | `USERNAME_EXISTS` | 用户名已存在 | 表单就地报错 |
| 1013 | `FORBIDDEN` | 禁止访问 | 提示无权限，不要重试 |
| 1014 | `TOKEN_REVOKED` | 令牌已被撤销 | 清凭证，跳登录 |
| 1015 | `USER_BANNED` | 用户已被封禁 | 展示封禁提示（HTTP 403） |
| 1016 | `EMAIL_EXISTS` | 邮箱已存在 | 表单就地报错 |

## 参数（2xxx → HTTP 400）

| 码 | 名称 | 默认文案 |
|----|------|----------|
| 2001 | `INVALID_PARAMS` | 参数无效 |

:::tip[具体原因在 msg]
同一个 2001 会带不同 `msg`（如「slug 已被占用」「token 值不能包含 ; { } < >」）。
客户端应展示 `msg` 而不是硬编码文案。
:::

## 资源（3xxx）

| 码 | 名称 | 默认文案 | HTTP |
|----|------|----------|------|
| 3001 | `NOT_FOUND` | 资源不存在 | 404 |
| 3002 | `ALREADY_EXISTS` | 资源已存在 | 409 |

## 限流与请求体（4xxx）

| 码 | 名称 | 默认文案 | HTTP |
|----|------|----------|------|
| 4001 | `RATE_LIMITED` | 请求过于频繁，请稍后再试 | 429 |
| 4002 | `BODY_TOO_LARGE` | 请求体过大 | 413 |

限流按「命名端点的每 IP 预算」+「全局每 IP 上限」两层。默认全局上限 60 次/分钟；
登录 / 注册等敏感端点有更小的独立预算。收到 429 应当退避，不要立即重试。

## 服务端（5xxx）

| 码 | 名称 | 默认文案 | HTTP |
|----|------|----------|------|
| 5001 | `INTERNAL_ERROR` | 服务器内部错误 | 500 |
| 5004 | `REQUEST_TIMEOUT` | 请求超时 | 504 |
| 5005 | `MAINTENANCE` | 站点维护中，请稍后再试 | 503 |

维护期间只放行读类 RPC；写请求会拿到 5005。

## 处理建议

```ts
// 前端典型处理：业务码决定交互，HTTP 状态只用于兜底
if (res.code === 1001 || res.code === 1002 || res.code === 1003 || res.code === 1014) {
  clearAuthTokens();
  redirectToLogin();
}
```

- **不要按 HTTP 状态分支业务逻辑**：`FORBIDDEN` 与 `USER_BANNED` 都是 403，语义不同
- **不要重试 4xx**：4xx 重试必然同样失败（`@feedchamber/api-client` 的 `shouldRetry` 只重试传输错误与 5xx）
- **封禁用户返回 404 而非 403** 是刻意设计：避免探测资源存在性
