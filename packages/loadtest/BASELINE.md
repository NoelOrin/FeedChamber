# 基线快照 · 2026-10-29

一次完整的匿名只读压测记录，供后续改动（缓存、扩容、SSR 优化）做前后对比。

## 被测对象

| 项 | 值 |
|----|----|
| 站点 | `https://dev-forum.noelorin.top`（Cloudflare → nginx → `backend:8080` / `frontend:3000`） |
| 部署档 | `deploy/docker-compose.yml` 默认档：postgres 16 + nats（JetStream）+ 单实例 backend + 单实例 frontend |
| 数据库 | PostgreSQL，`DB_MAX_OPEN_CONNS` 默认 25 |
| 客户端 | 单台 macOS arm64，k6 v2.3.0，单出口 IP，全程经 Cloudflare |
| 限流 | 后端全局每 IP 限流实测未生效（100 req/s 无 429）；CF 未返回 403/429 |

## 三轮结果

| 场景 | 并发 | 请求数 | 吞吐 | p50 | p95 | 失败率 | 429 / 403 | 结果 |
|------|------|--------|------|-----|-----|--------|-----------|------|
| 混合（真实浏览路径） | 0 → 1000，**约 200 中止** | 6,704 | 46.6 req/s | 1.55 s | 10.2 s | 2.13% | 0 / 0 | 触发中止保护 |
| 仅 API（`KINDS=json`） | 0 → 1000 跑完 | 112,650 | 234 req/s（平台期 ≈ **295 req/s**） | 1.5–1.8 s | 4.6 s | 0.02% | 0 / 0 | 完整跑完 |
| 仅 SSR 页面（`KINDS=html`） | 0 → 500，**约 171 中止** | 1,106 | 10.4 req/s | 5.1 s | 13.8 s | 2.89% | 0 / 0 | 触发中止保护 |

> 吞吐是整轮平均值（含爬坡期）；「平台期」是阶梯顶点前后按分钟差分得到的稳定值。
> p95 受 15s 请求超时影响——SSR 面打满时不是"变慢"，是**排队到超时**。

## 结论

1. **前端 SSR 是第一个瓶颈，而且离 API 差一个量级。**
   `/timeline`、`/spaces` 两页在约 150–200 并发浏览时 p50 就到 5 s、p95 14 s，页面上限 ≈ **10 req/s**；而同一时刻 API 面仍是 400 ms / 0 失败。混合场景的崩溃完全由 SSR 拖累，不是后端。
2. **API 面在千级并发下不报错，但吞吐封顶在 ≈ 295 req/s。**
   1000 并发完整跑完：112,650 请求、失败率 0.02%、无 5xx、无 429；代价是 p50 从 0.4 s 抬到 1.5–1.8 s、p95 4.6 s——典型的排队（队列在 DB 连接池 / 单实例后端 / CF 回源链路三者之一）。
   单端点看：`posts/list` 107 req/s（p50 1.55 s）、`posts/{id}` 61 req/s（p50 1.8 s），其余聚合端点 6–13 req/s。
3. **没有平台性拦截。** 三轮累计 12 万请求，`429=0`、`403=0`、`5xx=1`。Cloudflare 没把我们当攻击流量，后端全局限流也没开——所以这些数字是真实容量，不是被限流截断的结果。

## 复测：nginx 匿名 SSR 页面缓存上线后（同一天下午）

`deploy/nginx/nginx.conf` 加了 60s 共享缓存（匿名页、带会话/RSC 预取 bypass、`Vary` 忽略但请求头 bypass、3xx 也缓存）。

| 场景 | 指标 | 缓存前 | 缓存后 |
|------|------|--------|--------|
| 混合（真实浏览） | 完成度 | **200 VU 中止** | **1000 VU 跑完**（8m10s） |
| | 请求数 / 吞吐 | 6,704 / 46.6 req/s | **122,267 / 249.5 req/s** |
| | p95 / 失败率 | 10.2 s / 2.13% | **4.08 s / 0.06%** |
| SSR 页面面 | 完成度 | **171 VU 中止** | **500 VU 跑完**（4m） |
| | 请求数 / 吞吐 | 1,106 / 10.4 req/s | **24,127 / 98.2 req/s** |
| | p50 / 失败率 | 5.1 s / 2.89% | **1.73 s / 0.05%** |
| `GET /`（307） | p50 / 失败率 | 12.7 s / 44.6% | **0.5 s / 0.02%** |

- 页面面吞吐 **×9.4**，混合场景 **×5.4**，失败率降两个数量级；站点用同一套脚本、同一台客户端、同一条 Cloudflare 链路复测。
- 压测期间容器负载：nginx 5%（全部缓存命中）、frontend 25%、backend 30%、postgres 41%——瓶颈已经从 SSR 移回 API/DB。
- 剩下的天花板仍是 API 面的 ≈250–295 req/s（单实例后端 + `DB_MAX_OPEN_CONNS=25`）。再往上要么扩 backend 实例，要么调池/加缓存。

## 原因假设（需服务端确认）

- **SSR**：frontend 是单容器、compose 里没有 CPU 配额，vinext 每请求重渲染整页；页面级缓存（CDN/nginx `proxy_cache`）或 SSR→CSR 降级会直接抬上限。
- **API 平台期**：单实例 + `DB_MAX_OPEN_CONNS=25`，与「约 300 req/s 后 p50 线性上涨、错误率仍接近 0」的现象吻合。看 `feedchamber_http_request_duration` 与 DB pool wait 即可确认是排队还是计算。
- **Cloudflare 不缓存动态页**，所有页面请求都回源，CF 只是加了 ~200–350 ms 的往返，不承担容量。

## 复现

```bash
pnpm --filter @feedchamber/loadtest smoke                       # 端到端自检，必须 100%
k6 run -e KINDS=json -e PROFILE=api k6/stress.js              # API 面千级
k6 run -e KINDS=html -e MAX_VUS=500 -e PROFILE=ssr k6/stress.js   # SSR 面
k6 run -e PROFILE=mixed k6/stress.js                          # 混合（会早停，属预期）
```

## 读这份快照时注意

- 所有数字来自**单客户端、单 IP、经 Cloudflare**；换一台更近的机器或直接从内网打，绝对吞吐会不同，但「SSR ≪ API」的结论是结构性的，与链路无关。
- `2.13%` / `2.89%` 的失败几乎都是 15 s 超时，不是 5xx；报告里 `其它 4xx` / `5xx` 均为 0 可以印证。
- 中止是**脚本的保护**（`abortOnFail`），不是站点崩了；每轮结束后站点仍 200，ttfb ≈ 0.7 s。
